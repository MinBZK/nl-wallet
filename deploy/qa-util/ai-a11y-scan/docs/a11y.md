# How the accessibility scan works

## The idea

The e2e suite already visits every important screen of the app. As it does, it
can cheaply capture two artefacts per screen: the Appium **page source** (the
accessibility tree the platform exposes — the same data a screen reader sees)
and a **screenshot** (the rendered pixels). Those two together are enough to
check a meaningful subset of WCAG 2.1 AA statically, without a human driving a
screen reader through every screen on every build.

Capturing is gated on `ENABLE_A11Y_CAPTURES` (`captureA11ySnapshot` is a no-op
unless it is `true`), so the capture calls can live permanently in the tests and
only cost anything on the runs where you actually want captures. Pass it to the
e2e suite as a `-D` system property (`-DENABLE_A11Y_CAPTURES=true`);
`uiautomation/build.gradle.kts` forwards it — and the optional
`-DA11Y_CAPTURE_DIR` override — into the forked test JVM's environment, where
`MobileActions` reads it via `System.getenv`. The `-D` form is passed
per-invocation, so it works even with a reused Gradle daemon (a plain
`ENABLE_A11Y_CAPTURES=true` shell export needs `--no-daemon` to reach the test
JVM). See the [component README](../README.md) for full run commands.

`/a11y-scan` reads that folder of captures and, for each screen, walks the
[WCAG 2.1 AA ruleset](../.claude/skills/a11y-scan/wcag21aa.md): it reasons over
the page-source tree for name/role/label issues and reads the screenshot pixels
for colour and contrast. It writes the result in the **axe-core** report shape
so it slots into tooling and dashboards that already understand axe output.

## What it can and cannot see

**Checkable from a static capture:**

- Missing accessible names on images, icons, buttons, links, and inputs
  (WCAG 1.1.1, 4.1.2, 1.3.1, 3.3.2) — read from the page source.
- Text contrast (1.4.3) and non-text/UI contrast (1.4.11), and colour-only
  signalling (1.4.1) — read from the screenshot.
- Touch target size (2.5.5/2.5.8, `best-practice`) — measured from the page
  source's element geometry, converted to dp/pt with the `scale` in
  `<platform>.<environment>.device.json`. Android reports `bounds` in device
  pixels, so without that density the threshold cannot be applied and the check
  reports `incomplete` rather than guessing. There are two such files per
  platform — one per test run, since the BrowserStack device and the runner's
  own devices differ in density — and a disagreement between them also means
  `incomplete`.

**Not checkable from a static capture** (needs a live, interacting session, so
the scan does not report on them): focus visibility (2.4.7), keyboard/gesture
operability (2.1.x), motion/timing (2.2.x, 2.3.x), reflow at 400% zoom
(1.4.10), text-spacing overrides (1.4.12), orientation (1.3.4). These still
need manual or device testing.

The scan **reports aggressively** — it favours recall, so any rule condition
met on a visible element is raised as a `violation` even when it is unclear the
issue matters (a human, or `false-positives.md`, triages afterward). A judgement
call like decorative-vs-informative imagery is therefore flagged rather than
waved through. `incomplete` is reserved for the narrow case where the evidence
itself cannot be read — contrast on a photo/gradient where a single ratio is
not meaningful, or a node the page source under-describes — the axe convention
for "a human needs to check this". Nothing is dropped silently.

## Why axe form

axe-core is the de-facto accessibility result format, and the e2e suite already
runs BrowserStack's axe-based `wcag21aa` checks for the web surfaces. Emitting
the same shape means the native-screen findings can be read, diffed, and
aggregated with the same tools. The mapping to native captures:

- one axe *result object* per screen (the screen is the "page"; `url` is
  `<screen>@<platform>`);
- `nodes[].html` carries the page-source element snippet (no DOM exists);
- `nodes[].target` carries a native locator (resource-id / content-desc /
  xpath on Android, name / type+index on iOS);
- the check detail lands in `nodes[].any[]` with the rule id and `data`
  (contrast colours, ratio, …).

## What the report says it reviewed

The captures and the scan are not the same version of the app. Both capture
archives sit at one fixed MinIO path and are replaced per platform by whichever
e2e run last stored them, while the scan job runs on whatever commit is current
when it is triggered — so the Android captures, the iOS captures, and the scan
itself can all be three different commits, and `store-artifact.sh` tags the
published report with the last of those.

So the report records provenance per platform rather than once:
`capture_sources` in the JSON (plus `testEnvironment.commit` on each result
object, so one result is self-describing) and a `Captures: android @ … · ios
@ …` line in the Markdown. The values come from the `Git-Commit-Sha` attribute
the upload already stamps on each archive, read back with `mc stat` — not
inferred. A platform whose commit cannot be read is `unknown`; it is never
backfilled from the scan's own commit, because a wrong commit is worse than an
absent one when the question is "which build did these findings come from".

## Relationship to the security scan

This component is a sibling of `../ai-security-scan` and deliberately mirrors
its shape: a self-contained Claude Code skill under `.claude/skills/`, a
scoped tool allowlist in `.claude/settings.json`, a `false-positives.md` for
accepted findings, and reports that are gitignored review input rather than
committed content. The security scan reads source code; this one reads captured
app screens. Neither executes the target.

## Safety and trust model

This scan is safe because of **where it runs and what it reads**.

`.claude/settings.json` (`defaultMode: default`) grants Read/Glob/Grep/Task and
a set of search Bash commands, but also:

- `Write` and `Edit` — the skill writes its own `A11Y-REPORT.{json,md}`;
- `Bash(python3:*)` and `Bash(sips:*)` — the review subagents use these to
  sample exact screenshot pixels for contrast ratios (this is why the CI job
  installs Pillow).

`python3` is a general-purpose interpreter, so that last entry is effectively
arbitrary code execution: the scan *can* write outside its directory and *can*
open network connections. `Bash(find:*)` (`-exec`) is a second such path. The
skill is instructed to stay read-only beyond its report — "Do not write helper
scripts or pipe capture content into a shell interpreter" — but that is a
convention the model follows, not a boundary that is enforced.

We accept that deliberately instead of narrowing it, because the
prompt-injection surface is effectively nil. The captures are page source and
screenshots of **our own app**, produced by **our own e2e suite** from code in
this repository, and the ruleset and skill are committed here too. No
third-party or user-supplied content reaches the model. In CI the job runs in an
ephemeral container that is discarded after the run; locally it runs against
your own checkout.

Do not point `/a11y-scan` at captures from an untrusted source. That is the
one assumption the whole model depends on. Untrusted capture text would be an
injection vector with arbitrary code execution behind it.
